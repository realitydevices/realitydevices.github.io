## Implementation notes
- `updateItems()` projects `it.worldPos` directly via `.project(camera)` — fine for this slice, but the function is called from the animate loop and is *not* called from the resize handler at line 720. Under window resize, `_projected` is computed against a camera that has just had its frustum updated, but `updateItems` only re-runs on the next animation frame, and `it.el.offsetWidth` is read each frame (fine). However, the scene's `frustumSize = 60` is fixed, so on tall narrow viewports the world point `(28, 6, 18)` will project off the right edge of the screen because horizontal frustum scales with aspect. Worth a note: at aspect ratios < ~1.0, x=28 lands outside `[-frustumSize*aspect/2, +frustumSize*aspect/2]` once aspect drops below ~0.93. Slice-1 (the next slice) is the projection-correctness pass, so this is the implementer's open-question #2 in the changelog. Confirmed.
- `_camDir` is a poor variable name — it's actually `cameraWorldPosition` after `.normalize()` (line 659: `camera.getWorldPosition(_camDir).normalize()`). Reading it as "camera direction" is a small lie. The dot product against `it.anchorDir` is using *camera position direction from origin* as a proxy for *camera forward vector*. This works because the camera looks at the origin (orbit-around-fixed-target setup), so `cameraPos.normalize()` ≈ `-cameraForward`. Fine for now; will need to be `camera.getWorldDirection().negate()` (or just made explicit) once anything off the unit sphere starts mattering.
- The `anchorDirection` helper is still being used to produce a unit vector that is now *only* used for opacity, never for placement. The math is fine but the helper's name now lies — the result is no longer where the item *is*, it's only where the camera has to point to *see* it. Comment block at 626–636 documents this clearly enough; helper itself doesn't need renaming yet (still useful primitive).
- Probe is a stub. `probe.md` is the auto-generated "Capture ran without explicit probe instrumentation" placeholder. The spec's capture section explicitly required: "Probe must report the at-anchor and front views explicitly: where is the item relative to the logo silhouette in each." That didn't happen. The screenshots stand in for it adequately *this* pass, but the resize/perf checkpoint that's actually-load-bearing for Slice-1 will not be acceptable as a stub.
- No console output captured, no fps note. Single DOM card animating opacity + transform off `requestAnimationFrame` is not going to move the needle on perf, but per the spec's abandon criterion ("sustained <50fps after Pass 2") this needs to actually be measured at some point, not assumed.

## One concrete observation
The implementer's open-question #3 is the real one to resolve before Pass 5: with `worldPos` decoupled from `anchorDir`, the reveal curve can be at full opacity while the projected screen point is off-canvas or behind the camera. The current single placement happens to be in front of the camera at the anchor view so this is invisible *now*, but the invariant the implementer suggested (`dot(worldPos, anchorDir) > 0`, i.e. require worldPos to lie in the half-space the anchor faces) is the right shape — make it a soft assertion in `updateItems()` (dev-only `console.warn` when `_projected.z > 1` while reveal > 0.5) before adding the second item. Catching this with the first off-screen item under window resize is not the way you want to find out.
